The phone is busy.

That sounds like a fact about a person.

SIP is more careful.

[RFC 3261](https://www.rfc-editor.org/rfc/rfc3261.html) says a user agent server can return 486 Busy Here when the callee is not willing or able to take additional calls at that end system. If it knows that no other end system can accept the call, 600 Busy Everywhere is the stronger response.

The difference is epistemic scope.

486 says something local.

## "Here" is the important word

A SIP address can map to multiple contacts.

A user may have a desk phone, softphone, mobile client, and another registered endpoint.

One branch returning 486 tells a proxy something about that branch.

It does not necessarily tell the proxy that every branch is busy.

A forking proxy may continue trying others.

The protocol code preserves uncertainty intentionally.

## Endpoint knowledge is limited

An endpoint can know:

I am in another call.

Do-not-disturb is enabled.

The user rejected the call.

Local policy refuses another session.

It may not know:

another device is free,

the user is reachable through a different contact,

a downstream route will succeed,

or the caller could be redirected elsewhere.

The status code should not claim more than the endpoint knows.

That is a good design principle beyond SIP.

## Proxies transform local claims into routing decisions

A proxy receives responses from branches.

One returns 486.

Another times out.

Another returns 480.

The proxy has to choose what to do next and eventually what final response to send upstream.

Now interpretation enters.

The final response is not simply copied from reality.

It is selected according to transaction rules, routing logic, and observed branch outcomes.

The upstream caller sees a compressed summary of a distributed search.

## "Busy" is not a human state

Even 486 should not be read too literally.

It does not prove the human is physically talking.

A device may return 486 because local policy says no more calls.

The user may press reject.

A PBX may synthesize a response.

A gateway may map another network condition into 486.

The protocol exposes operational state, not direct access to human intention.

This is why CDR labels such as "busy" should be interpreted as signaling outcomes rather than psychological facts.

## Scope makes messages honest

Protocols become unreliable when participants make global claims from local evidence.

SIP avoids some of that by providing different response codes and routing behavior.

486 Busy Here is narrow.

600 Busy Everywhere is broader.

480 Temporarily Unavailable is different again.

Each code represents a particular level of knowledge and a particular kind of failure.

The vocabulary matters because proxies can react differently.

## Debugging should preserve the branches

When a call fails, the final code alone may hide the route history.

A useful trace asks:

Which contacts were tried?

Which branch returned 486?

Did another branch timeout?

Was the 486 generated by the endpoint or by an intermediary?

Did a policy engine rewrite it?

What final response did the proxy select?

Packet traces and transaction logs reveal the path the final code compressed.

## The protocol lesson

486 Busy Here is a small example of a large principle.

A system participant should report what it knows at the scope where it knows it.

Not more.

The phrase "the user is busy" is convenient.

The protocol's actual statement is narrower:

this destination, at this branch, is currently not accepting the call under the sender's local knowledge.

That small word *Here* is doing a lot of epistemic work.
