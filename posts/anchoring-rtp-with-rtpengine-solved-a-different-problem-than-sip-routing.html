The Media Must Go Somewhere: Understanding RTP Anchoring in VoIP Networks

A SIP call can be established while the conversation never arrives. Understanding why means separating the signaling path from the media path—and understanding what changes when a relay anchors RTP.

By Reaz Romen✓ Site verified
Published 2026-11-12 7 min read
RTPRTPengineSIPSDPNAT

A telephone call is an interesting illusion of simplicity. We dial a number, hear a ringtone, and eventually hear another human voice. From the user's perspective, everything appears to happen through one continuous connection. Underneath that experience, however, two different communication processes are taking place, and they do not necessarily follow the same network path.

One process establishes the call, negotiates its parameters and determines who should communicate with whom. The other carries the actual sound. This distinction is fundamental to Voice over IP. A SIP server can authenticate a user, process an INVITE, locate the destination and complete session negotiation, yet neither participant may hear anything. The call exists from the perspective of signaling, but the media path does not work.

This is where RTP media anchoring becomes important. To understand why RTPengine exists, we first need to understand why voice packets sometimes cannot travel directly between two endpoints, even when both endpoints have successfully established a SIP session.

Two different paths inside one telephone call

Consider Alice using a SIP phone on a private network and Bob using another phone somewhere else on the internet. Alice sends a SIP INVITE through the service's SIP infrastructure. The proxy routes the request, Bob's device responds, and the endpoints negotiate media parameters through Session Description Protocol (SDP).

SDP describes the proposed media session: IP addresses, UDP ports, codecs and other media capabilities. Alice might advertise an address and port like this:

c=IN IP4 192.168.1.20
m=audio 40000 RTP/AVP 0 8 101

The address belongs to a private network. Bob, on the public internet, cannot route packets directly to 192.168.1.20. Alice's SIP signaling may have crossed the network because she initiated an outbound connection to her provider, but that does not mean an incoming RTP stream can reach her phone. Signaling and media have different transport requirements and often different network paths.

Successful SIP signaling does not prove successful RTP connectivity. That one distinction explains a surprising number of silent calls and one-way-audio problems.

Why direct media can fail

In an ideal network, two endpoints exchange RTP directly. This is commonly called direct media or endpoint-to-endpoint media. It avoids sending continuous voice traffic through an additional server, and it can reduce infrastructure bandwidth and processing requirements.

But the public internet is not an ideal network. Residential and mobile networks commonly use Network Address Translation (NAT). A device receives a private address while its router translates outgoing traffic to a public address and maintains mappings for return traffic. The address written in an SDP message is therefore not necessarily an address another participant can reach.

A private address may be advertised to a public endpoint. The public UDP mapping may differ from the local port. A firewall may reject unsolicited incoming traffic, and NAT behavior can vary between networks. A SIP transaction can complete while the media packets are dropped, misdirected or never delivered.

There are techniques such as symmetric RTP and ICE that help endpoints discover and use viable media paths. They are important tools, but they do not remove every topology, policy or interoperability problem. Some services need a predictable media path under their own control.

What media anchoring changes

Media anchoring introduces an intermediate media relay. Instead of allowing Alice and Bob to send RTP directly to each other, both send their media to a relay, which forwards each stream to the other participant.

Signaling:
Alice  <------ SIP ------>  OpenSIPS / Kamailio  <------ SIP ------>  Bob
                                |
                                | NG control
                                v
                             RTPengine

Media:
Alice  <------ RTP ------>  RTPengine  <------ RTP ------>  Bob

The SIP proxy remains responsible for signaling. RTPengine handles the media session. The proxy instructs RTPengine to process the SDP offer and answer; RTPengine allocates media endpoints and rewrites the session description so that each participant sends media to the relay rather than to the other endpoint directly.

The important change is not merely that another server has been introduced. The negotiated media destination has changed. Alice now sends her RTP packets to RTPengine, and RTPengine forwards them toward Bob. The reverse direction works in the same way. The relay becomes an intentional point in the media path.

Following one media session

Imagine a lab with Alice behind a router and Bob on a reachable public address. The following addresses are reserved documentation examples, not real production endpoints:

ComponentAddress or portRole
Alice's phone192.168.1.20:40000Private-side RTP endpoint
Alice's NAT203.0.113.10Public address seen outside
Bob's phone198.51.100.20:50000Remote RTP endpoint
RTPengine203.0.113.50:30000Illustrative public media endpoint

First, Alice sends an INVITE containing an SDP offer. OpenSIPS or Kamailio processes the request and invokes RTPengine through its NG control protocol. RTPengine examines the SDP and allocates the media resources required for the session.

RTPengine then rewrites the media description presented to Bob. Rather than exposing Alice's private address, the offer identifies the relay's reachable media address. Bob returns an SDP answer, which is processed as well so that the two sides receive the appropriate relay destinations.

Once the session is established, Alice sends RTP toward RTPengine. The relay forwards the packets toward Bob. Bob's media follows the reverse path. The SIP proxy coordinates the session, but it does not need to carry the voice packets itself.

RTPengine is more than a UDP forwarder

It would be tempting to describe RTPengine as a process that receives packets on one port and sends them to another. That description misses the part that makes it useful. RTPengine maintains media-session state and understands SDP, streams and negotiated parameters. Depending on configuration and build capabilities, it can also provide functions that a generic UDP forwarder cannot.

SDP manipulation allows it to rewrite media addresses, ports and related session attributes. NAT-aware media handling helps the relay work with the addresses and ports actually observed on the media path. ICE support allows it to participate in candidate negotiation for environments that need ICE-based connectivity. It also supports secure-media scenarios, including SRTP, and can be configured for functions such as codec transcoding, recording and media forking.

These are not all automatic consequences of enabling a relay. They depend on the negotiated media profile, RTPengine build, configuration and the proxy's call-flow logic. A relay can anchor packets without transcoding them; it can also be asked to perform more work when the service requires it.

The cost of anchoring everything

If anchoring solves so many problems, why not route every call through RTPengine? Because every architectural solution introduces costs. Direct media avoids an extra media hop. Anchored media makes the relay part of the data path, and every packet must be received, processed and forwarded.

Bandwidth is the first consideration. A bidirectional call creates traffic in both directions, and the relay handles both the incoming and outgoing sides of those streams. Across hundreds or thousands of concurrent calls, the aggregate packet rate and network throughput become significant.

Latency is another consideration. The relay adds a network hop, and its physical location matters. A media server placed far from both participants can make an otherwise healthy call feel less responsive. CPU and packet-processing capacity also matter, particularly when transcoding, recording or other media operations are enabled.

Finally, the relay becomes a dependency. If RTPengine becomes unavailable, calls whose media is anchored through it can lose audio even while the SIP proxy remains healthy. Capacity planning, monitoring, redundancy and failure handling are therefore part of the design—not optional operational polish.

When should media be anchored?

There is no universal requirement to anchor every media session. The decision depends on topology, endpoint capabilities, security policy and the service's operational needs. Anchoring is useful when endpoints sit behind restrictive NAT, direct media is blocked by firewall policy, the service needs a controlled media route, address-family bridging is required, or recording, monitoring or transcoding must take place.

Direct media can be preferable when endpoints have reliable connectivity and the service does not need an intermediary for media processing or policy enforcement. A good architecture should make this a deliberate choice rather than assuming that every call has identical network requirements.

The relay has to be reachable too

RTPengine does not make network engineering disappear. It moves the media-path problem to a component designed to manage it. If RTPengine itself sits behind NAT or has multiple network interfaces, its internal address and externally reachable address must be configured and advertised correctly. The relevant firewall rules and UDP port ranges must also match the media configuration.

Incorrect interface selection can recreate the original failure one level deeper: SIP signaling succeeds, but endpoints receive an SDP address they cannot reach. A useful investigation therefore checks the SDP actually sent to each endpoint, the relay's selected interface, the firewall policy and the packets observed on both sides of the relay.

OpenSIPS and RTPengine solve different problems

In a production architecture, OpenSIPS or Kamailio handles signaling responsibilities such as registration, authentication, routing and call control. RTPengine handles media-session operations such as SDP-aware address rewriting, media anchoring and other configured media processing. The components communicate through RTPengine's NG control protocol.

The proxy must coordinate the media lifecycle correctly. Offers and answers can appear in more places than the initial INVITE and final 200 OK. Provisional responses, re-INVITEs and session updates can change SDP. Cancellation and call termination must also release the corresponding media state. Calling the media-management function only on one side of the initial exchange is not a complete call-flow design.

This separation allows signaling and media workloads to be scaled and managed independently, but it also means the proxy's routing logic must keep the two sides aligned. A media session is not simply created when a call starts; it may need to be updated as the session changes and must be released when the call ends.

A call is more than a successful response

A VoIP call is not one connection. It is a coordinated collection of signaling exchanges, negotiated media parameters, transport addresses, packet flows and network policies. SIP establishes the communication relationship. SDP describes the proposed media session. RTP carries the real-time audio. NAT and firewalls determine whether the network can actually deliver those packets.

RTPengine exists because these layers do not always cooperate naturally. Media anchoring gives the network an intermediate point where it can manage and control the media path without forcing the SIP proxy to carry the voice traffic itself.

A successful SIP response tells us that signaling has progressed. It does not tell us that a human voice can travel from one endpoint to another. In VoIP engineering, establishing a call and delivering a conversation are two different problems. RTPengine helps solve the second one.
